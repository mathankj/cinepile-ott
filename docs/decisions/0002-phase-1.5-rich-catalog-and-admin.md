# ADR-0002 — Phase 1.5: Rich catalog (movies + series), filters, browse rows, reactions, admin upgrade

**Status:** Accepted
**Date:** 2026-06-02
**Supersedes (partially):** ADR-0001 said "no recommendations, no profiles, no series" in V1. Some of those constraints relax in V1.5.
**Research feeders:** see `docs/research/2026-06-02-netflix-catalog.md` and `docs/research/2026-06-02-netflix-admin.md`

---

## Context

Client signed off on the POC and asked for the *real* Netflix-shaped flows: categories, series, episodes, languages, filters, recommendations, "newly added", admin uploads/edit/delete. V1 only covered single-film movies + a flat catalogue + basic admin.

We did web research on Netflix's actual catalog/browse flows AND its admin platforms (Backlot, Media Production Suite, Studio). Findings summarised in `docs/research/`. The decision below is what we promote from "interesting Netflix feature" into the build, and what we explicitly defer.

## The scope cut

Netflix has ~20 admin platforms, 8+ named recommendation rankers, a per-locale-per-A/B-variant image personalization service, IMF mastering, EIDR identifiers, regional rights windows, 7-role RBAC, lifecycle policies, multi-level QC, and a Data Canary that diff-checks every catalog mutation. Building all of that would take a team of 50 a year.

**Phase 1.5 builds the user-visible 80%** so the client's product can ship something that *looks* like Netflix to the end user. The studio-facing fulfillment workflow (Backlot equivalent), the ML recs, and the image perso layer become later phases.

### What we BUILD in V1.5

**Content model**
- `Title` table with `type IN ('movie','series')`.
- `Series` titles get `Season → Episode` children (Episode is the playable unit for series).
- Many-to-many `Genre` (renamed from `Category`).
- Many-to-many `Person` (cast + crew) — lightweight; just name + role.
- `audio_tracks` + `subtitle_tracks` per title (list of `{language, type}`).
- `availability_windows` per `(title, region)` — replaces a single `published_at`.
- `country_of_origin` (list of ISO 3166).
- `maturity_rating` (single + per-region overrides table).
- `EpisodeMarker` for skip-intro / skip-recap / credits-start.

**Lifecycle (single column `Title.status`)**
- `draft → scheduled → published → archived → removed`
- The Netflix Backlot has 13 states (planned/in-prod/in-post/delivered/inspection/qc_*/encoded/scheduled/live/expiring/removed/archived). We collapse upstream content-production states (planned, in_prod, in_post, delivered, qc_*, encoded) into a single bucket the client manages externally; our catalog only sees `draft` (not yet showable) → `scheduled` (publish at a future `publish_at`) → `published` (live, gated by availability windows) → `archived` (was live, no longer) → `removed` (license expired).
- `publish_at` lets admins schedule a future publish; a tiny background task (Phase 2 — for now a cron) flips `scheduled → published` when the time arrives. V1.5 also auto-promotes on-read if past `publish_at`.

**Roles** (`User.role`)
- `viewer` — read-only admin-panel access (introduced for trust-but-not-edit users; default for new admin staff).
- `content_manager` — full catalog write (create/update/publish/archive); cannot manage other users.
- `admin` — everything, including user management.
- The Netflix 7-role split (production_partner, fulfillment_partner, catalog_editor, localization_manager, qc_operator, content_manager, rights_manager, admin) is overkill for a single-studio client. Adopt content_manager as the "real Netflix catalog editor + rights manager combined" superset for V1.5. If the client ever onboards a third-party studio, we add `production_partner` then.

**User actions** (per-user, per-title — no profile sub-accounts yet)
- `Reaction` with `kind IN ('thumbs_down','thumbs_up','double_thumbs_up')` — matches Netflix's Apr-2022 three-state model.
- `WatchlistItem` (the "My List" equivalent).
- Episode-level `WatchProgress` (replaces V1's `WatchHistory`).

**Browse rows** — single new endpoint `GET /v1/home` returns a structured set of rows:
- `continue_watching` — most-recent in-progress titles (movies + series, ordered by `last_played_at DESC`, capped at 20).
- `my_list` — user's watchlist (capped at 50, `added_at DESC` then alpha).
- `new_releases` — titles published in last 30 days, region-aware, ordered by `published_at DESC`.
- `trending_now` — most-played in the last 7 days globally (will be region-aware in V2).
- `top_in_country` — equivalent to Netflix's Top 10, V1.5 returns top 10 by play count in last 7 days, region-aware.
- `because_you_watched` — for the user's most recently *finished* title, returns titles sharing ≥1 genre, excluding already watched. Multiple BYW rows can appear (one per recent finished title), capped at 3 such rows.
- `genre_rows` — for each of the user's top genres (by historical play time), one row per genre.

Row selection is the same for everyone in V1.5 (no per-user row reordering); ordering *within* rows is mostly time-based or popularity-based (no ML PVR yet). We document this and label it as "V1.5 heuristic" so V2 can swap in real rankers without breaking the API shape.

**Audit log** — every catalog write goes through a single `audit_log.record(actor, action, entity_type, entity_id, before, after)` helper. Append-only; never updated. Surfaced via `GET /v1/admin/audit`.

### What we DEFER

| Feature | Why deferred | When |
|---|---|---|
| IMF / EIDR / IMSC / MEC / BXF formats | Backlot-grade fulfillment is for licensed-studio delivery; our client is a single studio that uploads via our own UI | V3+ (if/when third-party studios) |
| Multi-region maturity-rating ladder beyond single override | Geo-targeting matters less for a single-region launch | V2 |
| Image personalization (multi-artwork A/B) | Requires ML infra + scale data | V3 |
| ML recommendations (PVR / Top-N / BYW Ranker) | Heuristics suffice while catalog is small | V3 |
| Multi-profile sub-accounts within one user | Real but additive; can layer on top of `User` later via `Profile` table | V2 |
| Lifecycle policy engine for asset tiering | Cold storage is V2 problem | V2 |
| Approval workflow (rights_manager sign-off before publish) | Single-studio client doesn't need multi-party approval | V2 |
| QC workflow / IaaS / redelivery | Same — single-studio uploads, no Backlot equivalent | V3 |
| Real CDN signed URLs | We return a self-signed JWT today; swap to CloudFront/Bunny later | V2 |

## Consequence: shape of the API

V1 had `/v1/films`. V1.5 has `/v1/titles` (unified). `/v1/films` is removed (project never shipped to anyone, no compat burden). Full new endpoint surface is in `docs/api/v1.md`.

The biggest shape change for clients: `WatchHistory` becomes `WatchProgress` and it's keyed differently for movies (one row per title) vs series (one row per episode). Continue-watching collapses episodes back up to series in the response.

## Alembic bootstrap

V1 used SQLAlchemy `create_all` for the dev DB. With this material schema expansion, we bootstrap Alembic now and let autogenerate capture the entire V1.5 schema as migration `0001_initial`. The V1 schema is a one-throwaway-DB-drop migration, not preserved. This is acceptable because nothing is in production yet.

## Migration plan (this PR)

1. New models + schemas + services + routes (this PR).
2. Bootstrap Alembic, autogenerate `0001_initial` from the V1.5 schema.
3. Reseed dev DB from the updated `scripts/seed_dev_data.py` (now includes 1 movie + 1 series with 2 seasons of 3 episodes + multi-lang audio + 2 genres + sample reactions + sample watchlist).
4. Update full test suite — every old test still passes (under renamed routes); new tests cover series, episodes, reactions, watchlist, browse rows, lifecycle states, role gating, audit log.
5. Re-run load smoke; append new numbers to `docs/runbooks/load-test-baseline.md`.

## What we will revisit

- If catalog size exceeds a few thousand titles, the `LIKE`-based search must move to Postgres `tsvector`. Already noted in catalog.py.
- If the "Trending 7d" row gets expensive, materialize it as a periodically-refreshed table (Phase 2 with Redis/Celery).
- If we add profiles, every per-user table becomes per-profile (Reaction, WatchlistItem, WatchProgress, ContinueWatching). Easier to bake in profiles from day 1 — but doing so before product-market-fit risks over-engineering. Tradeoff documented; not done now.
