# ADR 0003: Content protection via DRM

Status: Accepted (scaffolded, awaiting provider contract)
Date: 2026-06-03

## Context

OTT content cannot be meaningfully protected via JavaScript. The cosmetic
defences we shipped (right-click block, `controlsList="nodownload"`, the
visibility-curtain overlay) signal intent but do not stop:

- Screen recording (OBS, system screenshot tools, mobile screen-record)
- Direct manifest fetch + `yt-dlp` / `ffmpeg -i master.m3u8`
- Browser dev-tools network capture of segment URLs

The only real protection is **DRM** — the content is encrypted with a key
that the browser's GPU pipeline decrypts inside a secure path. The OS-level
HDCP enforcement is what makes Netflix screenshots come out black.

Three DRM systems cover every modern browser/OS:

| Key system | Browsers / devices | Notes |
|---|---|---|
| **Widevine** (Google) | Chrome, Edge (Chromium), Firefox, Android, Chrome OS, Smart TVs | Three security levels: L1 (hardware, allows HD/4K), L3 (software, SD only) |
| **PlayReady** (Microsoft) | Edge on Windows, Xbox, some Smart TVs | SL3000 (HW) / SL2000 (SW). Increasingly redundant on desktop now that Edge favours Widevine. |
| **FairPlay** (Apple) | Safari (macOS, iOS), tvOS | Uses HLS-AES-128 + app certificate + FPS license server. Different signing flow. |

Without all three, some users get blocked: e.g. Widevine-only excludes iPhone
Safari users.

systems, KYC is reasonable, has clear docs for HLS-CMAF packaging. Switch to
BuyDRM or Axinom only if EZDRM volume pricing becomes a problem.

## What we built so far (without paying for a provider)

The wiring is in. Nothing decrypts yet because there's no provider, but the
shapes are all there:

```
Backend                          Frontend
-------                          --------
core/config.py                   api/types.ts
  drm_widevine_license_url         DrmConfig {widevine_license_url, ...}
  drm_playready_license_url        PlaybackTicket { drm: DrmConfig | null }
  drm_fairplay_license_url
  drm_provider                   components/player/VideoPlayer.tsx
  drm_token_secret                 hls.js EME init when ticket.drm is set
                                   drmSystems passes license URL + token

services/playback.py
  _build_drm_config(user, ref)
  emits drm block on ticket
  signs license-request token

schemas/playback.py
  DrmConfig
  PlaybackTicket.drm
```

When you flip env vars on, the next playback request returns a `drm` block,
hls.js initialises EME, the browser fetches a license, the GPU does the
decryption. Zero code change from this point forward — only configuration +
content re-encoding.

## To turn DRM on (after signing with EZDRM)

1. **Get credentials from EZDRM** (or your chosen provider):
   - Widevine license URL (`https://widevine-proxy.ezdrm.com/proxy?pX=ABCDEF`)
   - PlayReady license URL
   - FairPlay license URL + app-certificate URL
   - Shared secret used to sign license-request tokens

2. **Put them in `backend/.env`:**
   ```
   DRM_PROVIDER=ezdrm
   DRM_WIDEVINE_LICENSE_URL=https://widevine-proxy.ezdrm.com/proxy?pX=...
   DRM_PLAYREADY_LICENSE_URL=https://playready.ezdrm.com/cency/preauth.aspx?pX=...
   DRM_FAIRPLAY_LICENSE_URL=https://fps.ezdrm.com/api/licenses/...
   DRM_FAIRPLAY_CERT_URL=https://fps.ezdrm.com/demo/video/eleisure.cer
   DRM_TOKEN_SECRET=<provider-supplied secret>
   ```

3. **Re-encode existing content with CENC encryption.** The unencrypted MP4s
   we have in B2 don't carry encryption metadata, so the player will error
   when it tries to fetch a license. You need one of:
   - **AWS Elemental MediaConvert** with the SPEKE preset → outputs
     CMAF/HLS with `EXT-X-KEY` lines pointing at the license server.
   - **Bitmovin Encoding** → similar output, easier UI.
   - **Shaka Packager (CLI)** → free, runs on your server. Slower but no
     extra vendor.

4. **Update the seeded `hls_manifest_url` rows** to point at the encrypted
   manifests instead of the clear ones.

5. **Verify:** play any title in Chrome. Network panel shows a POST to the
   Widevine proxy URL with a binary body (the license challenge). Player
   should keep playing. Open the same title on iOS Safari — it should
   negotiate FairPlay via the configured URLs.

## What does NOT need to change

- Backend playback gating (subscription + free flags) — unchanged.
- Frontend UI / settings gear / hover reveal — unchanged.
- Database schema — unchanged.
- The B2 storage layer — unchanged (encrypted MP4 segments still live in B2;
  only the bytes are different).

## What still won't be protected, even with DRM

- **Linux + Firefox** with Widevine L3 (software) — limited to SD per
  Google's policy. Many providers still allow streaming at lower quality.
- **HDCP-incompliant displays** — modern OS will refuse to output to a
  capture device that doesn't honour HDCP.
- **Camera pointed at a screen** — DRM doesn't help. Combined with **forensic
  watermarking** (Verimatrix, NAGRA) you can trace pirated copies back to
  the leaking user, but that's a separate product.

## Alternatives considered

- **No DRM, accept the risk.** Cheapest. Real for V1 because we don't yet
  have premium licensed content. Stop being viable the moment a content
  partner signs an exclusivity deal with us.
- **Clear-stream watermarking only.** Cheaper (~₹3k/mo) but defeats the
  point — no decryption barrier, only attribution post-leak.
- **DRM-locked .mkv downloads via dedicated apps.** Out of scope for a
  web-first product.

## When to revisit

- Within 30 days of signing the first content-licensing deal that mentions
  "DRM required" in its contract.
- Or when the first piracy incident shows up in monitoring (Google Alerts
  on the brand + Anti-Piracy tools like Friend MTS).
